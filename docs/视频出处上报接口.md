# 视频出处上报接口（给小主机 / Hermes）

> 版本：v1 ｜ 2026-09-25 ｜ 对接方：跑在黄总家小主机上的 Hermes
> 用途：把「帅哥录屏」每条稿件的原平台 / 原up主 送进小程序后端，
> 让粉丝在小程序解析结果页看到「原up主是谁」。

## 1. 一句话

发完一条视频，把这一条的出处 `POST` 到下面的地址即可。按 `bvid` 幂等，
**重复上报永远安全**，所以失败重发、全量重导都不会弄脏数据。

```text
POST https://api.beastnotes.cn/api/sources/ingest
X-Ingest-Token: <token>
Content-Type: application/json
```

token 由黄总转交（服务端环境变量 `SOURCE_INGEST_TOKEN`）。**不要写死在脚本里**，
从环境变量 `BIDONG_INGEST_TOKEN` 读取。

## 2. 请求体

三种形态都接受，单次最多 **500 条**：

```json
{ "items": [ { ... }, { ... } ] }
```

```json
{ "bvid": "BV15Pbj6yEKg", "platform": "douyin", "author_name": "小山坡" }
```

```json
[ { "bvid": "BV15Pbj6yEKg" }, { "bvid": "BV1txaT6nEz3" } ]
```

## 3. 字段

| 字段 | 必填 | 说明 |
|:--|:--|:--|
| `bvid` | ✅ | B站视频号，唯一键，形如 `BV15Pbj6yEKg` |
| `title` | | B站标题（最长 500） |
| `platform` | | `douyin` / `x` / `youtube` / `kuaishou` / `xiaohongshu` / `weibo` / `bilibili` / `other` / `unknown` |
| `author_name` | | 原作者昵称 |
| `author_handle` | | **平台上唯一、可搜索的账号标识**：抖音号 / X 的 screen_name / YouTube 的 @handle |
| `author_id` | | 原作者稳定 ID（昵称会改，用它关联） |
| `author_url` | | 原作者主页 |
| `source_url` | | 源视频链接 |
| `source_video_id` | | 源站视频 ID |
| `bili_published_at` | | B站发布日 `YYYY-MM-DD`（源站发布时间拿不到） |
| `note` | | 拿不到时的原因，例如 `parse失败 404` |

完整示例：

```json
{
  "items": [
    {
      "bvid": "BV15Pbj6yEKg",
      "title": "【小视频】126-减脂只是为了多吃",
      "platform": "douyin",
      "author_name": "小山坡",
      "author_handle": "xiaoshanpo123",
      "author_id": "MS4wLjABAAAAZYjMEsnl3xNTkMt-BeT6xJz6YHtZh4hX",
      "author_url": "https://www.douyin.com/user/MS4wLjABAAAAZYjMEsnl3xNTkMt-BeT6xJz6YHtZh4hX",
      "source_url": "https://v.douyin.com/Ou--3FzQeWs/",
      "source_video_id": "7681665368289533561",
      "bili_published_at": "2026-09-05",
      "note": ""
    }
  ]
}
```

**写作约定**

- 拿不到就留空 + `note` 写原因，**不要猜、不要用「未知」占位**。
- 一条视频只报一条「主要出处」= **画面来源**。混源视频（画面来自 X、BGM 来自抖音）
  只报画面来源，另一条不要报。
- `platform` 只能从源链接域名推断；推不出来的写 `unknown`。
- **`author_handle` 比 `author_name` 重要**：昵称可以改，改了粉丝按昵称就搜不到、
  甚至搜到别人。账号标识是唯一的，结果页的「复制原up账号」优先复制它，没有才退回昵称。
  - 抖音：抖音号（抖音 App 里「我 → 抖音号」那一串，**不是** `MS4wLjABAAAA…` 的 sec_uid）
  - X：`x.com/<screen_name>` 里的 screen_name，不带 `@`
  - YouTube：`youtube.com/@<handle>` 里的 handle，不带 `@`
  - 其它平台拿不到就留空。X / YouTube 的主页链接服务端也能自己推导，但不保证；
    抖音号只有解析响应里才有，必须由上报方提供。

## 4. 响应

```json
{"ok": true, "created": 12, "updated": 3, "rejected": []}
```

- `created` / `updated`：本次新增 / 覆盖更新的条数。
- `rejected`：被拒收的条目及原因，例如
  `[{"bvid": "BV1", "reason": "invalid bvid"}]`。

| 状态码 | 含义 |
|:--|:--|
| 200 | 已处理（**部分条目被拒也会返回 200**，看 `rejected`） |
| 400 | 请求体格式不对 / 超过 500 条 |
| 401 | token 不正确或没带 |
| 503 | 服务端还没配置 token |

## 5. 写入规则

- **幂等**：按 `bvid`，同一 bvid 只有一行，重复上报是覆盖更新。
- **空字段不覆盖**：某次上报里 `author_name` 为空，不会把之前已经补好的作者信息冲掉。
  所以「全量重导」或「只补平台的旧行」都不会造成信息倒退。
- `bvid` 不匹配 `^BV[0-9A-Za-z]{10}$` 时整条拒收，不写库。
- 单次超过 500 条整批 `400`，请自行分批。

## 6. 建议的上报流程（Hermes 侧）

```text
发布一条视频
  ├─ 解析源链接（本来就要做）→ 拿到 platform / author_* / source_*
  ├─ append 一行到 /root/.hermes/work/sources.jsonl     ← 先落盘，防丢
  └─ 调用 report_sources.py，把未发送的行批量 POST
        └─ 失败只记日志、不阻塞发布，留待下次重发（定时任务每小时兜底）
```

- 已成功发送的 bvid 记到 `/root/.hermes/work/sources.sent.jsonl`，避免重复发。
- 重发是安全的，所以状态文件丢了大不了全量重发一次。
- 支持 `--dry-run`：只打印将要发送的 JSON，不真发。
- 用本机已有的 HTTP 库，不要引入新依赖。

## 7. 自测

```bash
# 单条真实数据
curl -sS -X POST https://api.beastnotes.cn/api/sources/ingest \
  -H "X-Ingest-Token: $BIDONG_INGEST_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"items":[{"bvid":"BV15Pbj6yEKg","platform":"douyin","author_name":"小山坡","author_url":"https://www.douyin.com/user/MS4w"}]}'
# 期望：{"ok":true,"created":1,"updated":0,"rejected":[]}
# 再打一次同样的请求 → {"ok":true,"created":0,"updated":1,"rejected":[]}

# token 故意写错
# 期望：401
```

全量导入历史数据（`台账_出处回填_全量.csv`，124 行，含 14 条只有平台、没有作者的失败行）
按同样接口分批发送即可，`note` 照原样带过来。
