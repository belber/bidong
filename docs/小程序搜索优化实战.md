# 小程序搜索优化实战（微信搜一搜 / 页面收录）

> 来源：2026-09 在「壁咚咚藏链阁」上从 0 做了一轮收录优化的实测记录。
> 用途：以后做新小程序时照着做，不用重新踩坑。
> 原则：**标「实测」的是我们真跑过的结论，标「官方」的是微信文档要求，标「判断」的是我的推断，别当事实用。**

---

## 0. 一句话

微信搜索收录**不是配置问题，是入口问题**：sitemap 配对了也只是"允许收录"，
爬虫得先**发现**你的页面、打开后得**看到内容**，才会收录。
所以要做的就是三件事：**让 URL 自包含** → **未登录也能看** → **主动推送 + 分享入口**。

---

## 1. 机制：先搞清三件事

### 1.1 收录面板显示「-」不是 0

小程序后台「搜索 → 页面收录」显示"-"表示**还没有采到数据**，不是"收录了 0 个"。
数据是 **T+1** 更新，别一天刷十遍（实测：第一天全"-"很正常）。

### 1.2 爬虫长什么样

- **官方**：爬虫访问页面时 UA 含 `mpcrawler`，**场景值 1129**；
  还会带 `X-WXApp-Crawler-Timestamp / Nonce / Signature` 三个头，签名算法与消息推送一致
  （`token + timestamp + nonce` 字典序拼接后 sha1）。
- **实测**：页面里用 `wx.getLaunchOptionsSync().scene === 1129` 判断**最可靠**——
  请求头那两个线索在自建后端上不一定出现（微信那套头更常见于云托管/云函数场景）。
- **判断**：所以「爬虫来没来过」这件事，要在**小程序端按场景值上报**，不能只靠后端看请求头。

### 1.3 收录的前提条件（官方指南 6 条，按重要性排）

| 要求 | 说明 | 我们踩没踩 |
|:--|:--|:--|
| 页面 url 能**直接打开**，参数都在 url 里 | 不能依赖 `globalData`/`storage` 传参 | ❌ 踩了 |
| 必要时才要求授权登录 | 内容能匿名看就匿名看 | ❌ 踩了 |
| 页面标题、缩略图清晰 | `wx.setNavigationBarTitle` / `onShareAppMessage` | ❌ 没做 |
| 跳转优先用 `navigator` 组件 | 爬虫靠内链发现页面 | 判断：收益低 |
| 不收录 `web-view` 内容 | 官方明说做不到 | 我们没用 |
| 参数结构清晰、别塞 JSON | | 达标 |

## 2. 必修的四件事（每件都能单独生效）

### 2.1 内容页的 URL 必须自包含

**反例**（我们原来的写法）：解析完只写 `globalData` + `storage`，然后
`wx.navigateTo({ url: '/pages/result/result' })`。

后果有三个，而且不止影响爬虫：

- 爬虫打开 `/pages/result/result` → 页面是空的 → 不会被收录；
- 用户**分享这条页面**给别人 → 别人打开也是空的；
- 用户自己**重进/刷新**这条页面 → 数据没了。

**正确做法**：

```js
// 跳转时带上业务参数
wx.navigateTo({ url: '/pages/result/result?bvid=' + card.bvid });

// 落地页：先用手上已有的数据秒开，再按参数静默刷新（体验不倒退）
onLoad(options) {
  const bvid = (options && options.bvid) || '';
  const pending = getApp().globalData.pendingResult || wx.getStorageSync('pending_result');
  if (bvid) {
    const fresh = pending && pending.bvid === bvid;
    if (fresh) this.applyResult(pending);      // 秒开
    this.loadByBvid(bvid, { silent: fresh });  // 再拉最新，静默
    return;
  }
  this.applyResult(pending);                   // 老路径不能坏
}
```

### 2.2 未登录也要能看到内容

**反例**：结果页必须登录才有内容 → 爬虫/未登录访客看到的是一句「请先登录」。

**做法**：后端加一个**免登录的只读接口**，只回公开信息（标题/作者/封面/简介/业务字段），
**不含任何用户数据**；前端在拿不到登录态时自动降级渲染，把下载、导出这类需要身份的入口隐藏。

```python
# 后端：注意不要回 id / user_id / tags 这类用户维度字段
@router.get("/api/public/cards/{bvid}", response_model=PublicCardOut)
def public_card(bvid: str, db: Session = Depends(get_db)): ...
```

```js
// 前端：只在"认证类失败"时降级，业务错误照常报错
api.parse(url)
  .then(card => this.applyResult(card))
  .catch(err => {
    const authIssue = !err || !err.statusCode || err.statusCode === 401;
    if (!authIssue) { toast(err.message); return; }
    api.getPublicCard(bvid).then(card => this.applyResult(card, { publicView: true }));
  });
```

**顺带的好处**：新用户从外部进来先看到内容，再被引导登录，转化率也更好——
这不只是为了爬虫。

### 2.3 分享卡片指向"这一条内容"，并补上朋友圈

```js
onShareAppMessage() {
  return {
    title: this.data.title,                        // 用内容标题，别用产品名
    path: '/pages/result/result?bvid=' + this.data.bvid,  // 指向具体页
    imageUrl: this.data.coverUrl                   // 封面
  };
},
onShareTimeline() {                                // 朋友圈入口（容易漏）
  return { title: this.data.title, query: 'bvid=' + this.data.bvid, imageUrl: this.data.coverUrl };
}
```

**注意覆盖顺序**：如果多个页面共享一份公共分享配置，要小心谁覆盖谁。
我们项目里 `home.js` 是 `Page({ ...页面 }, pageShare)`（公共在后，会覆盖页面自己的实现），
而 `result.js` 自己定义了 `onShareAppMessage` 且**不展开公共配置**，所以没冲突。
两种混用时，公共配置放前面、页面自定义放后面。

### 2.4 动态设置导航标题

```js
wx.setNavigationBarTitle({ title: this.data.title + ' · ' + 品牌名 });
```

静态页（首页/帮助/关于）则在 `xxx.json` 里把 `navigationBarTitleText` 写成
**用户会搜的词**，比如「B站视频链接解析 · 壁咚咚藏链阁」，而不是「首页」。

## 3. 主动推送：比等爬虫快

### 3.1 两个阶段（微信自己的设计，务必利用）

| `@type` | 用途 |
|:--|:--|
| `wxsearch_testcpdata` | **审核数据**，只校验格式，不进搜索结果 |
| `wxsearch_cpdata` | **正式数据**，审核通过后才能推，会被检索到 |

先用审核数据把格式跑通，再去申请内容接入，通过后切正式数据。

### 3.2 请求结构（最小可用）

```http
POST https://api.weixin.qq.com/wxa/search/wxaapi_submitpages?access_token=ACCESS_TOKEN
```

```json
{
  "pages": [{
    "path": "pages/result/result",
    "query": "bvid=BV1xxxxxxxxx",
    "data_list": [{
      "@type": "wxsearch_cpdata",
      "update": 1,
      "content_id": "BV1xxxxxxxxx",
      "page_type": 2,
      "title": "标题（建议 20 字内）",
      "abstract": ["摘要，利于召回"],
      "cover_img_url": "https://...（有效期 15 天以上）",
      "mainbody": "正文，不能带 html 标签",
      "time_publish": 1700000000,
      "time_modify": 1700000100
    }]
  }]
}
```

**要点**

- `path + query` 是微信侧的唯一 id，**重复推等于覆盖更新**，所以可以放心重推。
- `update`：`1` 新增、`3` 删除。
- 每次 ≤ 1000 页，每天 ≤ 50 万页；增量建议单条推。
- `video` 结构化字段（`video_img` 要求 ≥686×288）**尺寸不达标就别填**，会被打回；我们没填。
- 建页面时**标题截断到 20 字**、正文剥掉 `<>`（不能带 html）。
- 正式数据要求：**页面能直接打开且打开就有内容**——所以第 2 节那两件事是前置条件。

### 3.3 access_token 要缓存

`/cgi-bin/token` 有调用频率限制，必须缓存（我们存 7200 秒，提前 5 分钟过期重取）。

### 3.4 错误码翻译成人话（运营看得懂才会去处理）

| 错误码 | 含义 | 处理 |
|:--|:--|:--|
| 85091 | 小程序的搜索开关被关闭 | 去小程序后台把「搜索」打开 |
| 108003 | 内容接入未审核通过 | 先申请，等审核 |
| 40066 | url 被 sitemap 拦截 | 检查 `sitemap.json` |
| 40211 | 数据结构校验失败 | 按返回的字段名改 |
| 47006 | 当天推送配额用完 | 明天再试 |
| 45002 | 请求包过大 | 分批 |

## 4. 观测：先回答"爬虫到底来没来过"

没有观测就只能瞎猜。用两条链路记录爬虫访问：

1. **小程序端按场景值上报**（最可靠）：

```js
// app.js：爬虫打开页面会带场景值 1129
onShow(options) {
  if (options && options.scene === 1129) {
    require('./utils/api.js').reportCrawlerVisit(options.path || '', queryString(options.query));
  }
}
```

2. **服务端按 UA / 请求头识别**：UA 含 `mpcrawler`，或带 `X-WXApp-Crawler-*` 头。
   配了「消息推送 Token」时还能验证签名，区分真假。

管理端做成一个页面，最上面给一句**结论**而不是一堆数字：

```
今天 0 次 → 「还没记录到爬虫访问。通常意味着微信还没发现这些页面：
              确认小程序已发布、后台搜索开关已打开，并用主动推送提交过页面。」
```

这样才分得清是"没入口"还是"页面是空的"——两种问题的解法完全不同。

## 5. 上线检查清单（新小程序照抄）

**基础**

- [ ] `sitemap.json` 允许收录（`{"rules":[{"action":"allow","page":"*"}]}`），`app.json` 里 `sitemapLocation` 指向它
- [ ] 每个静态页的 `navigationBarTitleText` 写成用户会搜的词
- [ ] 小程序后台：**打开「搜索」开关** + **申请内容接入**

**页面**

- [ ] 内容页 URL **自包含**（参数进 query，不靠 globalData/storage）
- [ ] 内容页**未登录也能看**（免登录只读接口 + 访客模式）
- [ ] 渲染后 `wx.setNavigationBarTitle` 设成内容标题
- [ ] 分享指向具体内容页（title / path / imageUrl），**朋友圈 `onShareTimeline` 别漏**

**推送**

- [ ] access_token 带缓存
- [ ] 先推 `wxsearch_testcpdata` 跑通格式，再切 `wxsearch_cpdata`
- [ ] 推送结果入库（时间/成功数/错误），管理端能看到
- [ ] 定时增量推送（新增/更新的内容），不必人工点

**观测**

- [ ] 爬虫访问记录（场景值 1129 + UA/请求头）
- [ ] 管理端给出"来过/没来过"的结论句

## 6. 常见误区（都是我们真踩过的）

| 误区 | 真相 |
|:--|:--|
| "sitemap 配了就会收录" | 只是**允许**收录；爬虫没入口照样 0 |
| "面板显示 0" | 是「-」，意思是**暂无数据**，不是 0；且 T+1 |
| "页面能打开就行" | 打开**没有内容**（要登录/依赖上下文）一样不会被收录 |
| "推一次就完事" | 内容更新要重推；`path+query` 相同是覆盖更新，重推很安全 |
| "爬虫会自己遍历所有页面" | 它主要靠**分享出去的链接**和**你主动推送**发现页面 |
| "后台点一下开关就完事" | 开关只管"能不能被搜"，页面质量与推送是另一回事 |

## 7. 附：本项目（壁咚咚藏链阁）的落地结果

> 2026-09-26 实测，可作为"做到什么程度"的参考。

| 项 | 结果 |
|:--|:--|
| 免登录公开接口 | `GET /api/public/cards/{bvid}`，被分享/被爬虫打开都能看到内容 |
| 推送审核数据 | 42 条页面一次通过（`errcode 0`） |
| 推送正式数据 | 42 条页面一次通过（说明搜索开关与内容接入都已就绪） |
| 自动推送 | 每天一次增量，开关在管理端 |
| 爬虫访问监控 | 管理端「搜索与收录」页（场景值 + 请求头两条链路） |
| 待观察 | 页面收录数何时开始出现——推送后通常需要几天 |

**一点克制**：这套东西对**工具类**小程序的自然流量帮助有限，核心流量还是靠站外导流。
投入顺序建议是：先做 2.1/2.2（同时是体验修复）→ 再做推送 → 最后才纠结收录数字。
